# TG Workbench

面向本地运营的 Telegram 群组、频道与话题镜像工作台。后端、管理 API 和 Web UI 打包成一个 Windows EXE，默认只监听 `127.0.0.1:8765`。

## 快速开始

1. 双击 `dist/TGWorkbench.exe`。
2. 浏览器打开 `http://127.0.0.1:8765`。
3. 在“系统设置”中保存一套从 `my.telegram.org` 获得的 Telegram API ID 和 API Hash。
4. 在“平台账号”中填写账号备注和手机号；只有需要使用另一套应用凭证的账号才启用独立 API 凭证。
   已有 Telethon 协议包时，也可点“导入协议包”选择包含一个 `.session` 和一个配套 JSON 的 ZIP。
5. 点击连接，在页面中提交 Telegram 验证码；账号启用两步验证时继续提交密码。
6. 登录后创建线路，从同步的对话列表选择来源和目标，也可手工填写 `-100...` Chat ID 与话题 ID。
7. 在线路上添加按序执行的内容规则，并用实时预览验证结果。

建议使用独立服务账号，不要使用承载个人隐私和资金操作的主账号。

## 已实现

- 一套全局 Telegram 客户端凭证可供多个自有账号复用，特殊账号可使用独立 API ID/Hash 覆盖
- 多 Telegram 用户账号、按账号独立加密 session、断线后的会话恢复
- Telethon SQLite 协议 ZIP 本机导入：严格校验 ZIP/SQLite，将授权材料转换后加密保存，导入后保持未连接
- Connector 注册表与能力声明；当前内置 Telegram，账号表单由 Connector 的凭证字段描述生成
- 线路级发送账号池；从在线且已加入目标会话的账号中轮询选择
- SQLite 持久发送队列：同一目标/话题严格串行，不同目标并行，程序重启后继续消费；等待页按最早任务展示阻塞原因和恢复时间，可重新检查限额或取消历史等待任务
- 按账号隔离 Flood Wait 冷却、指数退避、失败任务监控与重新入队
- 仅管理员、仅指定 User ID、管理员或名单、附加机器人账号等来源筛选；管理员列表自动缓存刷新
- 多来源到多目标、论坛话题匹配与目标话题发送
- 文本和说明文字的普通替换、正则替换、用户名/链接替换、前后缀
- 命中丢弃、命中审核、全量审核、审核改稿；手工消息可明确发往来源群或目标群，来源提问不会回显到目标
- 照片、视频、文件、语音、贴纸、联系人、位置、骰子的原样转发或无来源复制
- 相册按 `grouped_id` 聚合后整组发送
- 网址按钮转文字链接、全部按钮转文字或移除按钮
- OpenAI 兼容的全局 AI 内容处理：加密 API Key、可编辑全局/线路提示词、严格 JSON 决策、失败转审核或原规则发送
- 来源编辑和删除同步，持久化来源到目标的消息 ID 映射
- 账号对话同步、状态监控、操作日志和 Windows 自动启动
- SOCKS5 Telegram 代理
- 本地 Host 校验、安全响应头、1 MB API 请求限制
- 全局/账号级 API Hash 和 Telegram session 使用 AES-GCM；主密钥由 Windows DPAPI 绑定到当前用户
- AI API Key 同样存入加密 secrets，不写入普通设置 JSON，也不从管理 API 回传

## 明确限制

- Telegram 标记为受保护的内容不会被绕过或复制。
- 投票、实时位置、付费内容和部分服务消息在复制模式下进入审核；原样转发模式由 Telegram 决定能否发送。
- 审核队列当前只保存可编辑文本；批准特殊媒体审核项时会发送文本，不会重建投票或实时位置。
- 反应同步字段已预留，但当前不自动复制 reaction。
- 对话选择器当前读取最近 100 个对话，较旧会话可手工填写 Chat ID。
- 规则改写后以纯文本实体发送，原消息中的粗体、链接实体可能被重建为普通文本。
- Telegram callback 按钮绑定原机器人，用户账号无法复制其服务端回调。工作台只会把 URL/按钮标签转成文字或移除；Bot 命令菜单也不会冒充原 Bot 复制。
- 持久账号池队列当前用于文本、AI 改写结果、审核批准和手工插入。媒体与相册仍由监听账号实时复制/转发，后续版本需要落盘媒体任务才能做到崩溃后安全续传。
- 多账号只用于分担正常发送任务，不会绕过 Telegram Flood Wait、受保护内容或会话权限。每个池账号必须自行加入目标会话并具备发送权限。

## 构建

在 PowerShell 中运行：

```powershell
.\build.ps1
```

脚本会构建 Web UI、运行全部 Go 测试，并生成 `dist\TGWorkbench.exe`。上游 `uTLS 1.8.2` 的 Windows 发布包遗漏源码文件，因此 `go.mod` 固定到已修复该问题的上游提交 `880e27d8b0e5`，并使用包含安全修复的 Go 1.25.12 构建。

默认数据目录是 `%LOCALAPPDATA%\TGWorkbench`。可用 `-data` 指定测试目录，用 `-listen` 指定另一个本机回环端口。

## 运营建议

- 先用测试群验证每条线路，确认账号有来源读取权和目标发送权。
- 广告、联系方式、价格、收款信息建议配置 `review_if`，不要只做盲目替换。
- 同一来源不要配置相互回流的线路。工作台会忽略自己发出的更新，但无法判断其他机器人重新包装后的同内容消息。
- 关注 Telegram Flood Wait。账号池会冷却受限账号并持久重试，不会为规避平台限制而并发轰炸。

## Telegram 客户端凭证

API ID/Hash 标识的是 TG Workbench 使用的 Telegram 客户端应用，不是某个手机号的登录身份。一套有效应用凭证可供多个自有账号复用；每个手机号仍有独立的加密 Session、验证码流程和两步验证状态。

凭证解析始终按完整的一对处理：账号同时保存了 API ID 和加密 API Hash 时使用账号独立凭证，否则使用系统设置中的全局凭证，绝不会把账号 API ID 与全局 Hash 混合。升级前已存在的账号保留原有凭证并自动按独立凭证运行。全局和账号级 API Hash 都不会写入普通设置 JSON、账号列表或管理 API 响应。

## 导入 Telethon 协议包

“平台账号 → 导入协议包”只接受不超过 2 MiB 的 ZIP，包内必须恰好有一个标准 Telethon SQLite `.session` 和一个 JSON。JSON 需包含 `phone`、`app_id`、`app_hash`。工作台会拒绝路径穿越、多 Session、额外可执行文件、损坏 SQLite、异常 DC/端口和非 256 字节授权密钥。

导入只在本机完成：临时明文 Session 校验后立即删除，最终 gotd Session 和 API Hash 都进入 Vault 加密存储。导入不会自动连接 Telegram。删除账号时会先停止连接，再同时清理数据库记录和加密 Session。直登包 `tdata` 不属于 Telethon 格式，不能在这里导入。

购买的协议包可能被卖家复制；两份副本共用同一个 `auth_key` 时，Telegram 设备列表未必能把它们显示成两个可区分的设备。安全迁移方式是：先确认手机号、恢复邮箱和两步验证都由自己控制；协议包只用于临时取得访问权；随后删除导入账号，通过“添加账号”和正常验证码为 TG Workbench 建立全新的 Session，再从可信客户端撤销旧授权。撤销旧授权也会使所有旧副本失效。无法掌控手机号或恢复方式的购买账号不应承载客户隐私、收款或长期业务资产。

## AI 处理顺序

消息先经过确定性规则，再按线路选择调用 AI，最后执行人工审核或进入发送队列。AI 返回值必须是 `send`、`review` 或 `drop` 以及最终文本；正文被明确标记为不可信数据，不能覆盖系统约束。启动、账号登录、对话发现和未启用 AI 的线路不会调用 AI 服务。

## Connector 扩展

平台适配边界位于 `internal/connector`。账号、会话引用、标准消息和发送任务均带有 `platform`，发送 worker 只能领取自己平台的任务。标准消息包含文本、说明文字、回复 ID、线程键、按钮和附件描述；Connector 通过能力清单声明是否支持媒体、相册、编辑、删除、线程、URL 按钮、用户会话或 Bot Webhook。

新增平台时注册一个 `connector.Adapter`，实现账号创建、连接、验证、会话发现、审核发送和手工发送，并启动该平台自己的入站监听及队列消费者。`GET /api/connectors` 会把已安装平台、动态凭证字段和能力返回给管理面板。目标 `PeerRef.connectorId` 可指定该目标使用的平台账号；为空时继续使用线路账号池。

该抽象不表示各平台能力完全相同。跨平台线路必须按目标能力降级按钮、线程、编辑和媒体语义，并遵守平台官方 API、授权和限流要求。
